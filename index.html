Как я работаюHow I workпринципы из проектовprinciples from my projects

  • Схема процесса как источник правдыThe process diagram is the source of truth

    Свожу логику в схемы AS IS и TO BE в BPMN. Кто владеет шагом, где точки отказа и что будет при повторном входе клиента, решается по схеме, а не на созвонах.I put the logic into AS IS / TO BE diagrams in BPMN. Step ownership, failure points and repeated client entry are settled by the diagram, not in meetings.

  • Негативные сценарии до разработкиNegative scenarios before development

    Отказ скоринга, таймаут банка, повторная заявка с изменёнными данными попадают в требования заранее, а не всплывают дефектами на приёмке.Scoring rejection, a bank timeout, a repeated application with changed data go into requirements up front instead of surfacing as defects at acceptance.

  • Контракт раньше кодаContract before code

    API уходит в разработку с готовым контрактом в OpenAPI и тест-кейсами. Интеграции проверяю сам: Postman, SoapUI, логи в Kibana и Graylog.An API goes to development with a ready OpenAPI contract and test cases. I check integrations myself: Postman, SoapUI, logs in Kibana and Graylog.

  • Решения записаны в ADRDecisions are written down in ADRs

    Споры о принятых решениях снимает база ADR, а новые люди входят в контекст по документации, а не через расспросы.The ADR base settles arguments about past decisions, and new people get up to speed from documents rather than by asking around.

  • Типовое решение вместо разовой проработкиA standard path instead of one-off design

    Банки-партнёры подключаются по типовому сценарию на общей библиотеке методов. Новый банк добавляется настройкой справочника, без правок схемы и кода.Partner banks connect through a standard scenario on a shared method library. A new bank is a reference table entry, with no schema or code changes.

  • Документация для соседних командDocs for neighbouring teams

    Пишу инструкции для банков-партнёров и поддержки, чтобы спорные случаи и рутинные вопросы не доходили до разработчиков и аналитиков.I write guides for partner banks and support so disputed cases and routine questions don't land on developers and analysts.

Почему такWhy it looks like this

              
    
                
  • Ответ 202 вместо ожидания банка: рассмотрение идёт минуты, магазин не держит соединение и узнаёт итог из события.
    • 
                
  • Idempotency-Key: повтор после обрыва связи не создаёт вторую заявку.
    • 
                
  • Единая модель ошибки: магазин обрабатывает 409 по коду, а не по тексту сообщения.
    • 
                
  • Ключ сообщения applicationId: события одной заявки приходят по порядку.
    • 
              

              
    
                
  • 202 instead of waiting for the bank: a review takes minutes, so the store doesn't hold the connection and gets the result from an event.
    • 
                
  • Idempotency-Key: a retry after a dropped connection doesn't create a second application.
    • 
                
  • One error model: the store handles 409 by code, not by message text.
    • 
                
  • applicationId as the message key: events for one application arrive in order.

            ADR-007
            
Единый статус заявки через справочник статусов банковUnified application status via a bank status reference table

          

          

            Статус:Status: принятоaccepted
            Участники:Participants: аналитика, разработка конвейера, интеграцииanalysis, pipeline development, integrations
          

          

            
КонтекстContext

            
Каждый банк-партнёр возвращает свои коды статусов: буквенные, числовые, текстовые. Если соответствие зашито в адаптер банка, каждый новый банк и каждый новый код требуют релиза, а исходный ответ банка теряется.

            
Every partner bank returns its own status codes: letters, numbers, free text. If the mapping lives in each bank adapter, every new bank and every new code needs a release, and the bank's original answer is lost.

          

          

            
РешениеDecision

            
Заявка хранит два поля: единый статус и сырой код банка. Соответствие задаётся в справочнике bank_status_map. Неизвестный код не меняет единый статус и поднимает алерт для сопровождения.

            
An application stores two fields: the unified status and the bank's raw code. The mapping lives in the bank_status_map reference table. An unknown code leaves the unified status unchanged and raises an alert for the support team.

          

          

            
Рассмотренные вариантыOptions considered

            

              

                
ВариантOptionПлюсыProsМинусыCons

                
                  

                    Маппинг в коде адаптераMapping in adapter code
                    Быстро для первого банкаFast for the first bank
                    Новый банк или код означает релиз, логика размазана по адаптерамA new bank or code means a release; logic is spread across adapters
                  

                  

                    Справочник статусов (выбран)Status reference table (chosen)
                    Новый банк подключается строками в справочнике, сырой код сохраняется для разбора споровA new bank is just rows in the table; the raw code is kept for disputes
                    Справочнику нужен владелец, нужен алерт на неизвестный кодThe table needs an owner and an alert for unknown codes
                  

                  

                    Банки присылают наш форматBanks send our format
                    Маппинг не нуженNo mapping at all
                    Зависим от готовности каждого банка менять свой APIDepends on every bank agreeing to change its API
